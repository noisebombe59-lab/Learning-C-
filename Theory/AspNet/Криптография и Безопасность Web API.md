Криптография — это наука о методах обеспечения конфиденциальности, целостности данных и аутентификации сторон с помощью математических алгоритмов. Если говорить совсем просто: это искусство защищать информацию так, чтобы её не мог прочесть или изменить никто, кроме тех, у кого есть специальный ключ.
    
    1. Базовые понятия: Аутентификация vs Авторизация

Эти процессы происходят на бэкенде последовательно, но решают совершенно разные задачи.

Аутентификация (Authentication) — «Кто ты такой?» Процесс проверки личности пользователя. Пользователь предъявляет паспорт, вводит логин/пароль или передает цифровой токен. Сервер проверяет эти данные и говорит: «Да, ты действительно Илья».

Авторизация (Authorization) — «Что тебе разрешено?» Процесс проверки прав доступа. Происходит строго после аутентификации. Сервер проверяет, имеет ли подтвержденная личность право совершить действие. Сервер говорит: «Так, Илья — Junior-разработчик. Ему можно читать данные акций, но удалять базу данных нельзя».

Порядок в конвейере Middleware (Program.cs)
Порядок вызова методов имеет критическое значение для безопасности приложения:
    
    app.UseAuthentication(); // 1. Проверяем паспорт (Кто это?) 
    app.UseAuthorization();  // 2. Проверяем права (Куда ему можно?)

Важно: UseAuthentication всегда идет первым. Система физически не может проверить права доступа пользователя (Авторизацию), пока не установит, кем именно является этот пользователь (Аутентификация).

    2. Хранение состояния: Куки против JWT-токенов

Интернет-протокол HTTP «амнезичен» — он не помнит предыдущие запросы. Чтобы сервер узнавал пользователя при каждом следующем клике, используют один из двух подходов.

Подход 1: Традиционные Куки (Сессионный подход)
Что передается клиенту: Сервер выдает браузеру только случайный, уникальный номер — идентификатор сессии (например, SessionID = 777).

Где хранятся данные: Все реальные данные пользователя (Id, роли, имя) лежат строго на сервере (в оперативной памяти или быстрой базе данных Redis).

Как это работает: Пользователь делает запрос $\rightarrow$ Браузер автоматически шлет номер 777 $\rightarrow$ Сервер берет этот номер, идет в свою память/базу, ищет там карточку №777, читает права и разрешает действие.

Плюс: Мгновенный контроль. Если админ банит пользователя, сервер стирает сессию 777 из памяти, и пользователя тут же выкидывает из системы.

Минус: Высокая нагрузка. Сервер вынужден на каждый чих пользователя делать лишний запрос в память, что снижает производительность при миллионах юзеров. Это чисто браузерная технология, с ней неудобно работать на мобилках.

Подход 2: Современные JWT-токены (Стандарт для Web API)
Что передается клиенту: Сервер не хранит сессии у себя. Он выдает пользователю полноценный цифровой паспорт — строку, где внутри зашифровано: {"Name": "Илья", "Role": "Developer"}.

Где хранятся данные: Строка токена хранится у самого клиента (в памяти мобильного приложения или хранилище браузера).

Как это работает: Пользователь делает запрос $\rightarrow$ Прикрепляет строку токена $\rightarrow$ Сервер проверяет математическую подпись своим секретным ключом. Подпись совпала? Сервер прямо из текста токена читает, кто ты. В базу данных он не идет.

Плюс: Нулевая нагрузка на БД. Сервер экономит колоссальные ресурсы и работает максимально быстро, проверяя токены «на лету» процессором. Идеально подходит для любых устройств (мобилки, ПК, сторонние сервера).

Минус: Задержка при блокировке. Сервер не ходит в базу, поэтому не узнает о бане пользователя, пока у токена не истечет его собственный срок действия. Поэтому JWT всегда делают короткоживущими (на 5–15 минут).

    3. Анатомия JWT-токена (JSON Web Token)

JWT — это текстовая строка, состоящая из трех частей, разделенных точками: Header.Payload.Signature

Header (Заголовок): Техническая информация (тип токена и алгоритм шифрования, например HS256). Генерируется .NET автоматически.

Payload (Полезная нагрузка): Данные пользователя (Имя, Роли, Издатель). Бэкенд читает эти данные мгновенно без обращений к SQL-базе.

Signature (Подпись): Защита от взлома. Сервер берет Header и Payload, добавляет к ним свой секретный ключ из appsettings.json и сжимает в криптографический хэш. Если хакер изменит данные в Payload, подпись перестанет совпадать, и сервер заблокирует запрос.

Разбор терминологии настроек в Program.cs
При конфигурации TokenValidationParameters в .NET мы задаем правила для «охранника» на входе в API:

Issuer (Издатель): URL-адрес или имя сервера, который выпустил токен (наш бэкенд, например http://localhost:5243). Защита от токенов, выпущенных сторонними серверами.

Audience (Потребитель): URL-адрес фронтенда (или приложений), для которых этот токен предназначался. Гарантирует, что токен используется именно там, где разрешено.

IssuerSigningKey (Ключ подписи): Секретная строка (соль) из настроек, которой сервер подписывает токены.

Encoding.UTF8.GetBytes(...): Метод перевода текстового секретного ключа в массив байтов (чисел). Криптографические алгоритмы процессора не умеют работать с человеческим текстом, им нужны чистые числа для математической проверки подписи.

Как сборка JWT выглядит в коде .NET (Три главных инструмента):
Вместо ручного склеивания строк, фреймворк использует три системных класса, которые работают как конвейер:

SecurityTokenDescriptor («Чертеж») — объект, куда мы складываем все настройки будущего токена: кому выдан (Subject через клейма), кем выпущен (Issuer), сколько живет (Expires) и какую цифровую подпись использовать (SigningCredentials).

JwtSecurityTokenHandler («Завод/Сборщик») — берет этот «чертеж» и методом CreateToken() собирает C#-объект токена в памяти.

Метод .WriteToken() — финальный этап. Он берет готовый объект токена, превращает его данные в JSON, кодирует в Base64Url и выдает ту самую финальную длинную строку для клиента.

    4. Различения: Хэширование, Шифрование, Кодирование
Архитектурные зоны защиты

Хранение данных (База данных): Защищается через UserManager.CreateAsync. Пароль необратимо преобразуется в хэш. При компрометации базы данных исходные пароли остаются в безопасности.

Транспортировка данных (Сеть): Защищается через JWT-токены и конфигурацию IssuerSigningKey. Секретный ключ используется сервером для генерации цифровой подписи токена и её валидации при каждом входящем запросе.

    Хэширование (В одну сторону)

Направленность: Превращение данных в уникальную строку фиксированной длины.

Ключ: Не используется.

Обратимость: ❌ Необратимо. Восстановить исходный текст из хэша невозможно никакими методами. Администратор сервера или разработчик не имеют технического доступа к паролям пользователей. Единственный способ деанонимизации хэша — полный перебор комбинаций (Brute Force).

Применение: Хранение паролей в БД, коммиты в Git (SHA-1), контрольные суммы файлов.

Что такое Соль (Salt) в хэшировании

Суть:
Это случайная уникальная строка криптографического мусора. Она автоматически генерируется для каждого пользователя и принудительно подмешивается к его паролю перед тем, как превратить его в хэш.

Формула:
Хэш = Алгоритм(Пароль пользователя + Уникальная соль)

Зачем это нужно (Защита от Радужных таблиц):
Хакеры давно создали Радужные таблицы (Rainbow Tables) — гигантские базы данных, где заранее сосчитаны хэши для миллиардов популярных паролей (например, слово "password" всегда дает один и тот же хэш). Если хакер украдет базу данных без соли, он мгновенно узнает пароли по этим таблицам.

Соль ломает эту схему: даже если два пользователя выберут абсолютно одинаковый пароль "12345", из-за разной соли их хэши в базе данных будут совершенно непохожими. Перебор по готовым таблицам становится бесполезным.

Как это работает в .NET:
Тебе не нужно создавать соль вручную. Когда ты вызываешь UserManager.CreateAsync(user, password), встроенный в .NET Identity адаптивный алгоритм сам генерирует соль, хэширует пароль и сохраняет итоговую строку в колонку PasswordHash.

Сама соль уже вшита внутрь этой строки, поэтому сервер знает, как правильно извлечь её и проверить пароль при будущей авторизации.

    Шифрование (В обе стороны)
Направленность: Способ превратить читаемую информацию в нечитаемую, чтобы её никто не смог прочитать без специального ключа. Обратимо (процесс расшифрования).

Два главных вида шифрования:
Симметричное шифрование

Используется один и тот же ключ и для шифрования, и для расшифровки (как один ключ от шкафа).

Очень быстрое. Пример: AES-256.

Используется, когда обе стороны уже имеют общий секрет (например, в VPN или при шифровании файлов).

Асимметричное шифрование

Используется два ключа: публичный и приватный (как почтовый ящик: прорезь доступна всем, а ключ от дверцы только хозяину).

Публичный ключ — можно давать всем, им только шифруют сообщение.

Приватный ключ — хранится строго у владельца, им расшифровывают сообщение.

Медленнее симметричного. Пример: RSA, ECC.

Гибридное шифрование (Самое важное в практике)
Это комбинация асимметричного и симметричного шифрования. Используется почти везде (HTTPS, WhatsApp, Telegram, VPN).

Как работает:

Асимметричное шифрование (медленно, но безопасно) $\rightarrow$ Используется только один раз в начале сессии для безопасной передачи сгенерированного случайного симметричного ключа.

Симметричное шифрование (быстро) $\rightarrow$ После безопасной передачи ключа все дальнейшие данные сессии шифруются одним этим общим симметричным ключом.

Итог: Асимметричное — решает проблему безопасной передачи ключа в сети. Симметричное — обеспечивает высокую скорость шифрования потока данных.

Применение: HTTPS (безопасное соединение с сайтами), Мессенджеры, VPN, банковские приложения, цифровые подписи.

    Кодирование (Изменение формата)

Направленность: Перевод данных в удобный для компьютера или сети формат.

Ключ: Не используется.

Обратимость: Обратимо (процесс декодирования). Секретности нет, любой может вернуть исходный текст без ключей.

Применение: Перевод текста в байты (UTF-8), упаковка бинарных данных в текст (Base64).

Encoding.UTF8.GetBytes(...) — криптографические алгоритмы (например, HmacSha512) физически не умеют работать с человеческим текстом (string). Поэтому секретный ключ (Signing Key) из appsettings.json перед созданием подписи обязательно переводится в массив байтов (byte[]). Без этого процессор не сможет провести математические вычисления хэша.

    5. Algoritms хэширования: SHA-256 против BCrypt
SHA-256 (Криптографический спринтер)

Характеристика: Спроектирован для максимальной скорости обработки больших массивов данных.

Применение: Генерация подписи JWT-токенов (HS256), проверка целостности файлов, блокчейн-сети.

Уязвимость: Из-за высокой производительности уязвим к атакам перебором (Brute Force) на видеокартах, поэтому непригоден для хэширования паролей.

BCrypt / PBKDF2 (Адаптивный тяжеловес)

Характеристика: Намеренно замедленный алгоритм. Использует вычислительный фактор (Work Factor) для создания искусственной задержки (около 0.1 сек).

Применение: Хранение паролей (используется под капотом в .NET Identity).

Преимущество: Сводит скорость перебора хакерами к минимуму. Автоматически применяет «Соль» (Salt) — случайную строку, добавляемую к паролю для защиты от дешифровки по заготовленным таблицам.

    6. Логика Login и авторизация в .NET
1. Архитектурное разделение обязанностей (Менеджеры)
Identity разделяет процесс входа на два независимых этапа. За каждый этап отвечает свой встроенный сервис.

UserManager<AppUser> — отвечает за поиск сущности в БД.

Метод: _userManager.Users.FirstOrDefaultAsync(x => x.UserName == loginDto.Username.ToLower())

Суть: Нам нужно просто вытащить объект пользователя по его уникальному имени (или Email), чтобы понять, существует ли он.

SignInManager<AppUser> — отвечает за проверку подлинности (аутентификацию).

Метод: _signInManager.CheckPasswordAsync(user, loginDto.Password, lockoutOnFailure: false)

Суть: Этот менеджер берет сырой пароль из DTO, автоматически достает из объекта user соль и хэш, склеивает их, перемалывает через SHA-256 и сравнивает результаты.

2. Параметр LockoutOnFailure (Блокировка аккаунта)
Метод CheckPasswordAsync принимает третий bool параметр — защиту от брутфорса (перебора паролей).

lockoutOnFailure: true — включает счетчик ошибок. Если пользователь введет неверный пароль несколько раз подряд, Identity временно заморозит аккаунт (по умолчанию на 5 минут).

lockoutOnFailure: false — отключает заморозку. На этапе разработки всегда ставим false, чтобы не заблокировать самого себя при тестировании из-за случайной опечатки.

3. Криптографическая гигиена (Безопасность ответов)
Запрещено давать хакеру подсказки о том, какая именно часть данных неверна.

Нарушение безопасности: Возвращать "Пользователь не найден" или "Неверный пароль". Это позволяет злоумышленнику составить список существующих в системе логинов.

Стандарт защиты: При любой ошибке (не найден юзер или не совпал хэш) возвращаем строго 401 Unauthorized с одинаковым размытым сообщением:

"Invalid username and/or password"

4. Конфигурация Swagger под JWT (Схема Bearer)
По умолчанию Swagger «голый» и не умеет прокидывать токены. Чтобы тестировать эндпоинты с атрибутом [Authorize], в Program.cs внутри метода builder.Services.AddSwaggerGen(...) настраивается схема авторизации.
