        1. DTO (Data Transfer Object)
Это «посылка». Мы не отправляем клиенту всю модель из базы (с паролями и лишними связями), а создаем упрощенную копию. Это защищает от Over-posting (когда хакер пытается обновить поля, которые не должен трогать).

        C#
        // Модель в БД (Тяжелая)
        public class Stock {
            public int Id { get; set; }
            public string Symbol { get; set; }
            public decimal LastDiv { get; set; } // Лишние данные для списка
        }
        
        // DTO для клиента (Легкая)
        public class StockDto {
            public string Symbol { get; set; }
        }

        // Маппер (Метод расширения)
        public static StockDto ToStockDto(this Stock stockModel) => 
            new StockDto { Symbol = stockModel.Symbol };
.

        2. Инъекция зависимостей (DI) и Сроки жизни
Мы не создаем объекты через new, а просим их в конструкторе. Это делает код гибким (как LEGO).

Transient: Новый объект на каждый «чих».

Scoped: Один объект на один HTTP-запрос (идеально для БД).

Singleton: Один на всё время работы сервера.

        C#
        public interface ITransientService { int GetNumber(); }
        public class TransientService : ITransientService 
        {
            private static int _globalCounter = 0;
            private readonly int _number;
        
            public TransientService()
            {
                _globalCounter++; // Увеличиваем общий счетчик
                _number = _globalCounter; // Запоминаем номер этого конкретного объекта
            }
            public int GetNumber() => _number;
        }

// Точно такие же классы делаем для Scoped и Singleton...
// (Они отличаются только названиями, чтобы DI-контейнер их различал)
Шаг 2: Тестируем в Контроллере
Мы точно так же просим в конструкторе по две штуки каждого сервиса:

        C#
        [HttpGet]
        public IActionResult Get()
        {
            return Ok(new
            {
                // Просим номера у двух Transient сервисов
                Transient1 = _transient1.GetNumber(),
                Transient2 = _transient2.GetNumber(),
        
                // Просим у двух Scoped
                Scoped1 = _scoped1.GetNumber(),
                Scoped2 = _scoped2.GetNumber(),
        
                // Просим у двух Singleton
                Singleton1 = _singleton1.GetNumber(),
                Singleton2 = _singleton2.GetNumber()
            });
        }
А теперь смотрим на цифры в ответе:
Вызываем эндпоинт в САМЫЙ ПЕРВЫЙ РАЗ (Запрос №1):
Transient1 = 1, Transient2 = 2.
(Почему? Родился первый объект, счетчик стал 1. Тут же для второго параметра родился второй объект — счетчик стал 2).

Scoped1 = 3, Scoped2 = 3.
(Почему? Для этого HTTP-запроса создался ОДИН объект. И первому, и второму параметру выдали его. Счетчик стал 3).

Singleton1 = 4, Singleton2 = 4.
(Почему? Создался один объект на всё время работы сервера. Счетчик стал 4).

Нажимаем обновить страницу (Запрос №2):
Transient1 = 5, Transient2 = 6.
(Прошлые умерли, родились два абсолютно новых).

Scoped1 = 7, Scoped2 = 7.
(Для нового HTTP-запроса родился один новый объект с номером 7).

Singleton1 = 4, Singleton2 = 4.
(А вот он НЕ ПЕРЕСОЗДАЛСЯ. Он остался жив с прошлого запроса, его номер по-прежнему 4).

        3. Middleware (Промежуточное ПО):
Стоит самым первым. Проверяет запрос «в целом» (Битый ли JSON? Тот ли протокол? Огромный ли размер файла?). Он не знает деталей твоего C#-кода.

   [ApiController] и ModelState (Уровень MVC): Запускаются следом. Фреймворк берет JSON, наполняет твой DTO и проверяет все атрибуты ([Required], [Range]), записывая результаты в словарь ModelState.

Магия «Автопилота»:
Раньше разработчики вручную писали проверку в каждом методе:

        C#
        // Тедди писал это для наглядности, но в реальном коде это НЕ НУЖНО:
        if (!ModelState.IsValid) return BadRequest(ModelState);
Благодаря атрибуту [ApiController] над классом контроллера, этот код работает на автопилоте. Он автоматически проверяет ModelState.IsValid для всех методов. Если в DTO есть ошибка, фреймворк сам перехватит запрос до запуска твоего кода и вернет клиенту 400 Bad Request с детальным описанием ошибок.

        4. Базовые понятия: Аутентификация vs Авторизация

Эти процессы происходят на бэкенде последовательно, но решают совершенно разные задачи.

Аутентификация (Authentication) — «Кто ты такой?»
Процесс проверки личности пользователя. Пользователь предъявляет паспорт, вводит логин/пароль или передает цифровой токен. Сервер проверяет эти данные и говорит: «Да, ты действительно Илья».

Авторизация (Authorization) — «Что тебе разрешено?»
Процесс проверки прав доступа. Происходит строго после аутентификации. Сервер проверяет, имеет ли подтвержденная личность право совершить действие. Сервер говорит: «Так, Илья — Junior-разработчик. Ему можно читать данные акций, но удалять базу данных нельзя».

        5. Порядок в конвейере Middleware (Program.cs)
В ASP.NET Core правила проверки запросов настраиваются через Middleware. Порядок вызова методов имеет критическое значение для безопасности приложения:

app.UseAuthentication(); // 1. Проверяем паспорт (Кто это?)
app.UseAuthorization();  // 2. Проверяем права (Куда ему можно?)

Важно: UseAuthentication всегда идет первым. Система физически не может проверить права доступа пользователя (Авторизацию), пока не установит, кем именно является этот пользователь (Аутентификация).

        6. Хранение состояния: Куки против JWT-токенов
Интернет-протокол HTTP «амнезичен» — он не помнит предыдущие запросы. Чтобы сервер узнавал пользователя при каждом следующем клике, используют один из двух подходов.

Подход 1: Традиционные Куки (Сессионный подход)
Что передается клиенту: Сервер выдает браузеру только случайный, уникальный номер — идентификатор сессии (например, SessionID = 777).

Где хранятся данные: Все реальные данные пользователя (Id, роли, имя) лежат строго на сервере (в оперативной памяти или быстрой базе данных Redis).

Как это работает: Пользователь делает запрос $\rightarrow$ Браузер автоматически шлет номер 777 $\rightarrow$ Сервер берет этот номер, идет в свою память/базу, ищет там карточку №777, читает права и разрешает действие.

Плюс: Мгновенный контроль. Если админ банит пользователя, сервер стирает сессию 777 из памяти, и пользователя тут же выкидывает из системы.

Минус: Высокая нагрузка. Сервер вынужден на каждый чих пользователя делать лишний запрос в память, что снижает производительность при миллионах юзеров. Это чисто браузерная технология, с ней неудобно работать на мобилках.

Подход 2: Современные JWT-токены (Стандарт для Web API)

Что передается клиенту: Сервер не хранит сессии у себя. Он выдает пользователю полноценный, зашифрованный цифровой паспорт (строку, где внутри написано: {"Name": "Илья", "Role": "Developer"}).

Где хранятся данные: Строка токена хранится у самого клиента (в памяти мобильного приложения или хранилище браузера).

Как это работает: Пользователь делает запрос $\rightarrow$ Прикрепляет строку токена $\rightarrow$ Сервер проверяет математическую подпись своим секретным ключом. Подпись совпала? Сервер прямо из текста токена читает, кто ты. В базу данных он не идет.

Плюс: Нулевая нагрузка на БД. Сервер экономит колоссальные ресурсы и работает максимально быстро, проверяя токены «на лету» процессором. Идеально подходит для любых устройств (мобилки, ПК, сторонние сервера).

Минус: Задержка при блокировке. Сервер не ходит в базу, поэтому не узнает о бане пользователя, пока у токена не истечет его собственный срок действия. Поэтому JWT всегда делают короткоживущими (на 5–15 минут).

        7. Анатомия JWT-токена (JSON Web Token)
JWT — это текстовая строка, состоящая из трех частей, разделенных точками: Header.Payload.Signature

Header (Заголовок): Техническая информация (тип токена и алгоритм шифрования, например HS256). Генерируется .NET автоматически.

Payload (Полезная нагрузка): Данные пользователя (Имя, Роли, Издатель). Бэкенд читает эти данные мгновенно без обращений к SQL-базе.

Signature (Подпись): Защита от взлома. Сервер берет Header и Payload, добавляет к ним свой секретный ключ из appsettings.json и сжимает в криптографический хэш. Если хакер изменит данные в Payload, подпись перестанет совпадать, и сервер заблокирует запрос.

        8. Разбор терминологии настроек в Program.cs
При конфигурации TokenValidationParameters в .NET мы задаем правила для «охранника» на входе в API:

Issuer (Издатель): URL-адрес или имя сервера, который выпустил токен (наш бэкенд, например http://localhost:5243). Защита от токенов, выпущенных левыми серверами.

Audience (Потребитель): URL-адрес фронтенда (или приложений), для которых этот токен предназначался. Гарантирует, что токен используется именно там, где разрешено.

IssuerSigningKey (Ключ подписи): Секретная строка (соль) из настроек, которой сервер подписывает токены.

Encoding.UTF8.GetBytes(...): Метод перевода текстового секретного ключа в массив байтов (чисел). Криптографические алгоритмы процессора не умеют работать с человеческим текстом, им нужны чистые числа для математической проверки подписи.

        9. Безопасность на разных платформах (Почему мир не выбрал что-то одно?)

В Браузерах опасен JWT: В браузерах работает JavaScript. Если хранить JWT в обычном LocalStorage, вредоносный скрипт (XSS-атака) может украсть токен целиком. Защищенную куку с флагом HttpOnly JavaScript прочитать не может. Поэтому для браузерных сайтов куки безопаснее.

В Мобильных приложениях безопасен JWT: В мобилках (iOS/Android) нет дырявого браузерного JavaScript окружения, а токен надежно прячется в изолированное системное хранилище телефона (Keychain/Keystore). При этом сервер не тратит память на хранение сессий миллионов мобильных устройств.

Бэкенд как «Черный ящик»: Бэкенд-код выполняется скрыто на удаленном сервере. Хакер не может подсмотреть переменные или секретные ключи в оперативной памяти сервера. Самые защищенные системы веб-сайтов совмещают технологии: генерируют быстрый JWT-токен, но передают его внутрь защищенной HttpOnly Куки, полностью скрывая данные от JavaScript.

1. Архитектурные зоны защиты
Хранение данных (База данных): Защищается через UserManager.CreateAsync. Пароль необратимо преобразуется в хэш. При компрометации базы данных исходные пароли остаются в безопасности.

Транспортировка данных (Сеть): Защищается через JWT-токены и конфигурацию IssuerSigningKey. Секретный ключ (строка "SigningKey" в настройках) используется сервером для генерации цифровой подписи токена и её валидации при каждом входящем запросе.

2. Различия: Хэширование, Шифрование, Кодирование
Хэширование (В одну сторону)
Направленность: Превращение данных в уникальную строку фиксированной длины.

Ключ: Не используется.

Обратимость: ❌ Необратимо. Восстановить исходный текст из хэша невозможно никакими методами.

Применение: Хранение паролей в БД, коммиты в Git (SHA-1), контрольные суммы файлов.

Шифрование — это способ превратить читаемую информацию в нечитаемую, чтобы её никто не смог прочитать без специального ключа.
Два главных вида шифрования:
1. Симметричное шифрование

Используется один и тот же ключ и для шифрования, и для расшифровки.
Очень быстрое.
Пример: AES-256.
Используется, когда обе стороны уже имеют общий секрет (например, в VPN или при шифровании файлов).

2. Асимметричное шифрование

Используется два ключа: публичный и приватный.
Публичный ключ — можно давать всем, им шифруют сообщение.
Приватный ключ — только у владельца, им расшифровывают сообщение.
Медленнее симметричного.
Пример: RSA, ECC.

Гибридное шифрование (самое важное в практике)
Это комбинация асимметричного и симметричного шифрования. Используется почти везде (HTTPS, WhatsApp, Telegram, VPN и т.д.).
Как работает:

Асимметричное шифрование (медленно, но безопасно)
→ Используется только один раз для безопасной передачи симметричного ключа.
Симметричное шифрование (быстро)
→ После передачи ключа все дальнейшие данные шифруются одним общим симметричным ключом.

Простая схема:

Браузер / приложение генерирует случайный симметричный ключ.
Шифрует его публичным ключом сервера.
Сервер расшифровывает его своим приватным ключом.
Дальше вся переписка/данные идут через симметричный ключ (быстро и эффективно).

Почему так делают?

Асимметричное — решает проблему безопасной передачи ключа.
Симметричное — обеспечивает высокую скорость шифрования.

Гибридное шифрование = безопасность + скорость

Простое правило:

Симметричное = один общий ключ (как один ключ от шкафа).
Асимметричное = два ключа (как почтовый ящик: прорезь всем, ключ только хозяину).

Где используется:

HTTPS (безопасное соединение с сайтами)
Мессенджеры (WhatsApp, Signal, секретные чаты Telegram)
Шифрование паролей (на самом деле хэширование)
VPN, банковские приложения, цифровые подписи

Главное преимущество: Даже если данные перехватили, без правильного ключа их невозможно прочитать.

Кодирование (Изменение формата)
Направленность: Перевод данных в удобный для компьютера или сети формат.

Ключ: Не используется.

Обратимость: Обратимо (процесс декодирования). Секретности нет, любой может вернуть исходный текст без ключей.

Применение: Перевод текста в байты (UTF-8), упаковка бинарных данных в текст (Base64).

3. Алгоритмы хэширования: SHA-256 против BCrypt
SHA-256 (Криптографический спринтер)
Характеристика: Спроектирован для максимальной скорости обработки больших массивов данных.

Применение: Генерация подписи JWT-токенов (HS256), проверка целостности файлов, блокчейн-сети.

Уязвимость: Из-за высокой производительности уязвим к атакам перебором (Brute Force) на видеокартах, поэтому непригоден для хэширования паролей.

BCrypt / PBKDF2 (Адаптивный тяжеловес)
Характеристика: Намеренно замедленный алгоритм. Использует вычислительный фактор (Work Factor) для создания искусственной задержки (около 0.1 сек).

Применение: Хранение паролей (используется под капотом в .NET Identity).

Преимущество: Сводит скорость перебора хакерами к минимуму. Автоматически применяет «Соль» (Salt) — случайную строку, добавляемую к паролю для защиты от дешифровки по заготовленным таблицам.

4. Главный вывод по безопасности данных
Администратор сервера или разработчик не имеют технического доступа к паролям пользователей. Единственный способ деанонимизации хэша — полный перебор комбинаций (Brute Force), против которого эффективно работают медленные алгоритмы (BCrypt, PBKDF2) и сложные пароли.
