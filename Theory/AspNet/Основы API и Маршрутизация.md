1. Что такое API и Эндпоинты
   
API — это «внешняя оболочка» программы. Фронтенд (сайт или мобилка) не знает, как устроена твоя база, он просто стучится в конкретные «двери» — Эндпоинты.

Формула эндпоинта: URL + HTTP Глагол (например, GET /api/stock).

2. Маршрутизация (Routing) и [ApiController]
Система навигации, которая связывает URL с методом в C#.

Атрибут [ApiController] — это твой «автопилот». Он сам проверяет ошибки ввода и понимает, откуда брать данные.

        C#
        [ApiController] // "Автопилот": сам вернет 400 Bad Request, если данные — мусор
        [Route("api/stock")] // Общий путь для всех методов в этом контроллере
        public class StockController : ControllerBase 
        {
            [HttpGet("{id}")] // Конкретный путь: api/stock/5
            public IActionResult GetById([FromRoute] int id) 
            {
                return Ok();
            }
        }

4. CreatedAtAction (Тот самый сложный метод)
Этот метод — вершина вежливости твоего API. Он не просто говорит «создано», он дает визитку с адресом.

Синтаксис:

    C#
    return CreatedAtAction(
        nameof(GetById),         // 1. Имя метода, который может показать этот объект
        new { id = model.Id },   // 2. Параметры для этого метода (чтобы собрать URL)
        model.ToStockDto()       // 3. Сами данные, чтобы фронтенд сразу их отрисовал
    );
Зачем это нужно: В заголовках (Headers) ответа появится поле Location. Фронтенд может взять эту ссылку и сразу перенаправить пользователя на страницу новой акции.

4. Атрибуты-источники ([From...])
Эти атрибуты говорят системе, где именно в HTTP-запросе искать данные. Без них ASP.NET может запутаться.

[FromBody]: Говорит: «Данные лежат в теле запроса в формате JSON». Используется для POST и PUT.

[FromRoute]: Говорит: «Возьми данные прямо из URL». Например, если URL api/stock/5, то [FromRoute] int id выцепит цифру 5.

[FromQuery]: Используется для фильтрации. Если URL api/stock?symbol=AAPL, то атрибут вытащит значение AAPL.

Метод расширения (Твой ручной маппер)
В твоем коде была конструкция model.ToStockDto(). Это не встроенная фишка C#, а Extension Method (метод расширения). Это способ «приклеить» свой метод к уже существующему классу.

Как это работает:

Создаешь статический класс.

Пишешь статический метод.

Используешь ключевое слово this перед первым аргументом.

    C#
    public static class StockMapper 
    {
        // Теперь у любого объекта Stock появится метод .ToStockDto()
        public static StockDto ToStockDto(this Stock stockModel) 
        {
            return new StockDto {
                Symbol = stockModel.Symbol,
                Purchase = stockModel.Purchase
                // Мы НЕ копируем сюда коллекцию Comments, чтобы избежать цикла!
            };
        }
    }
Зачем это нам: Это позволяет держать контроллер чистым. Вместо того чтобы внутри каждого метода GET писать new StockDto { ... }, ты просто вызываешь короткое .ToDto().

1) Как избежать зацикливания: В зависимости от того, что именно ищет пользователь в данный момент, роли распределяются так:Ищем автора $\rightarrow$ Автор главный, книги второстепенные $\rightarrow$ убираем у книг ссылку на автора.Ищем книгу $\rightarrow$ Книга главная, автор второстепенный $\rightarrow$ убираем у автора ссылку на книги.

5. Миграции 
Что это: Это «чертеж» изменений. Когда ты меняешь свои классы (модели) в C#, миграция описывает, как перенести эти изменения в реальные таблицы SQL.

Зачем нужно: Чтобы не лазить в SQL Server руками. База данных должна всегда соответствовать твоему коду. Миграции позволяют синхронизировать базу у всей команды разработчиков.

Нюанс: Миграция — это не сама база, это лишь инструкция (код на C#), которая говорит базе: «Добавь колонку» или «Удали таблицу».

1). Три главные команды (Инструментарий)
Работа происходит в консоли (Package Manager Console).

Add-Migration [Имя] — Создать чертеж. EF Core сравнивает твои модели с последним снимком и генерирует файл миграции.

Update-Database — Применить чертеж. EF Core идет в SQL и выполняет все новые инструкции. Только после этого база реально изменится.

Remove-Migration — Сжечь чертеж. Удаляет последнюю созданную миграцию (работает только если ты еще не успел нажать Update-Database).

2). Анатомия файла миграции (Up и Down)
Каждая миграция состоит из двух методов. Это как «Шаг вперед» и «Шаг назад».

Метод Up: Инструкции по обновлению. (Например: CreateTable).

Метод Down: Инструкции по откату, если что-то пошло не так. (Например: DropTable).

    C#
    // Пример: Добавили поле "Описание" в модель Stock
    protected override void Up(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.AddColumn<string>(
            name: "Description",
            table: "Stocks",
            nullable: true);
    }

    protected override void Down(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.DropColumn(
            name: "Description",
            table: "Stocks");
    }
3). Model Snapshot (Снимок состояния)
В папке Migrations всегда лежит файл ...ModelSnapshot.cs.

Что это: Это финальный, итоговый чертеж всей твоей базы в одном файле.
Зачем нужно: Когда ты пишешь Add-Migration, EF Core не лезет в реальный SQL. Он сравнивает твои текущие классы с этим «снимком».
Важно: Никогда не удаляй и не меняй этот файл вручную! Это «память» системы.

4). Переименование полей (Ловушка потери данных)
Это самый опасный момент. Если ты просто переименуешь свойство в C# (например, Title в Name), EF Core может решить, что ты удалил Title (со всеми данными!) и создал пустой Name.

Как делать правильно:

Создай миграцию через Add-Migration.

Зайди в созданный файл.

Если видишь там DropColumn и AddColumn — удали их и напиши вручную migrationBuilder.RenameColumn. Это сохранит данные внутри колонки.

5). Таблица истории (__EFMigrationsHistory)
Что это: Секретная таблица, которую EF Core сам создает в твоей базе данных.
Зачем нужно: Там хранится список имен всех миграций, которые уже были применены. Когда ты пишешь Update-Database, система смотрит в эту таблицу и понимает: «Так, миграции №1 и №2 уже стоят, а №3 — новая, запускаю её».

6. IActionResult — это стандартный способ метода контроллера сказать: «Вот что случилось с твоим запросом».

✅ Успех (2xx)
Ok(данные) — 200 OK. «Всё в порядке, вот то, что ты просил». (Самый частый ответ для GET).

CreatedAtAction(...) — 201 Created. «Я создал объект, найти его можно вот по этому адресу». (Для POST).

NoContent() — 204 No Content. «Я всё сделал (например, удалил), но данных в ответ не пришлю». (Для DELETE/PUT).

❌ Ошибки клиента (4xx)
BadRequest() — 400 Bad Request. «Ты прислал некорректные данные (ошибка валидации)».

Unauthorized() — 401 Unauthorized. «Я тебя не знаю, сначала залогинься».

Forbid() — 403 Forbidden. «Я знаю кто ты, но у тебя нет прав на это действие».

NotFound() — 404 Not Found. «Я искал в базе, но по этому ID ничего нет».

💥 Ошибки сервера (5xx)
Problem() — 500 Internal Server Error. «Упс, у меня в коде что-то упало (ошибка в логике или БД)».

    [HttpPost]
    public async Task<IActionResult> Create([FromBody] CreateStockDto dto) 
    {
        var model = dto.ToModel();
        await _context.Stocks.AddAsync(model);
        await _context.SaveChangesAsync();
        
        // Возвращаем 201 статус и путь к новому объекту
        return CreatedAtAction(nameof(GetById), new { id = model.Id }, model.ToStockDto());
    }
Суть: Ты возвращаешь не просто «объект или пустоту», а конкретный статус-код, чтобы фронтенд точно знал, выводить данные или показывать ошибку.
