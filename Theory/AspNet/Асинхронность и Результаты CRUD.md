1. Сервер имеет ограниченный набор потоков (Thread Pool). Если каждый поток будет просто сидеть и ждать ответа от базы данных (I/O операция), то при наплыве пользователей новые запросы встанут в очередь, и сервер «умрет», хотя процессор будет загружен всего на 1%.

Task — это объект, который представляет собой асинхронную операцию и позволяет взаимодействовать с ней после запуска.

async: Модификатор, который разрешает использовать await и заставляет компилятор превратить твой метод в «стейт-машину» (способную останавливаться и возобновляться).

await: Это команда отпустить поток. Поток возвращается в пул и может обрабатывать запросы других юзеров. Когда база данных присылает данные, любой свободный поток подхватывает твой метод и продолжает его выполнение с того же места.

Визуализация в коде: Асинхронный контроллер

    C#
    [HttpGet("{id}")]
    public async Task<IActionResult> GetStockById([FromRoute] int id) 
    {
        // 1. Поток (Thread) зашел в метод.
        // 2. Доходим до await. Поток дает команду базе "Ищи!" и ТУТ ЖЕ уходит.
        // Пока база работает (например, 200мс), этот поток уже обслуживает другого юзера.
        var stock = await _context.Stocks.FirstOrDefaultAsync(x => x.Id == id);

        // 3. Когда база ответила, "проснувшийся" поток (может быть уже другой) 
        // возвращается сюда и проверяет результат.
        if (stock == null) 
        {
            return NotFound();
        }
    
        return Ok(stock.ToStockDto());
    }

2. I/O Операция — это любое действие, когда твоя программа выходит за пределы своей оперативной памяти, чтобы пообщаться с внешним миром.

Простые примеры:

Диск: Сохранить файл на ПК или прочитать конфигурацию из JSON.

Сеть: Загрузить картинку с сайта или отправить запрос на другой сервер.

База данных: Попросить SQL-сервер выдать список пользователей.

Давай так же просто и без лишней терминологии пересоберем эти два понятия.

3. I/O-Bound задача
Это задача, скорость которой упирается исключительно в скорость внешнего мира (интернета, жесткого диска или стороннего сайта).

Как ведет себя программа: Она отправляет запрос наружу и просто замирает в ожидании. Процессор компьютера при этом ничем не занят, он отдыхает.

Как это решается (async/await): Чтобы программа не простаивала мертвым грузом, мы говорим ей: «Пока ты ждешь ответа от сети, отпусти свой поток (рабочую силу) обратно в систему, пусть он обработает другие запросы. А как данные прилетят — продолжишь».

4. CPU-Bound задача
Это задача, скорость которой упирается в мощность твоего процессора. Тут нет никакого ожидания, программа все делает сама внутри себя.

Как ведет себя программа: Она загружает процессор на все 100%. Поток непрерывно работает: крутит тяжелые циклы, перебирает огромные массивы данных, шифрует пароли или архивирует файлы.

Как это решается (Task.Run): Чтобы эта тяжелая работа не заморозила всё приложение (например, чтобы кнопка «Отмена» на экране продолжала нажиматься), мы берем эту задачу и руками переносим её на соседний, фоновый поток. Основной поток остается свободным и приложение не «зависает».

5. Thread Pool (Ресурс «рук»)
Это ограниченный набор потоков сервера.

Если задача I/O синхронная: Поток «замерзает» и сидит без дела, пока база отвечает. Ты тратишь ценный ресурс впустую.

Если задача I/O асинхронная: Поток дает команду «Ищи!» и возвращается в Thread Pool, чтобы обработать запрос другого клиента. Когда база ответит, любой свободный поток подхватит работу.

Логическая цепочка в коде (Квинтэссенция)

    C#
    public async Task<IActionResult> GetStock(int id) 
    {
        // 1. I/O Bound (Ждем базу)
        // Используем await, чтобы освободить Thread Pool.
        var stock = await _context.Stocks.FirstOrDefaultAsync(x => x.Id == id); 
    
        if (stock == null) return NotFound();
    
        // 2. CPU Bound (Работаем в памяти)
        // Данные уже в RAM. Процессор быстро их перекладывает. 
        // await тут не нужен — это мгновенная работа самого CPU.
        var dto = stock.ToStockDto(); 

    return Ok(dto);
    }
Итог одной фразой:
Используй Async/Await для I/O Bound задач (база, сеть), чтобы не транжирить Thread Pool на бесполезное ожидание, и оставляй CPU Bound (логика в памяти) синхронным, так как это работа самого процессора.
    
6. IActionResult — это стандартный способ метода контроллера сказать: «Вот что случилось с твоим запросом».

✅ Успех (2xx)
Ok(данные) — 200 OK. «Всё в порядке, вот то, что ты просил». (Самый частый ответ для GET).

CreatedAtAction(...) — 201 Created. «Я создал объект, найти его можно вот по этому адресу». (Для POST).

NoContent() — 204 No Content. «Я всё сделал (например, удалил), но данных в ответ не пришлю». (Для DELETE/PUT).

❌ Ошибки клиента (4xx)
BadRequest() — 400 Bad Request. «Ты прислал некорректные данные (ошибка валидации)».

Unauthorized() — 401 Unauthorized. «Я тебя не знаю, сначала залогинься».

Forbid() — 403 Forbidden. «Я знаю кто ты, но у тебя нет прав на это действие».

NotFound() — 404 Not Found. «Я искал в базе, но по этому ID ничего нет».

💥 Ошибки сервера (5xx)
Problem() — 500 Internal Server Error. «Упс, у меня в коде что-то упало (ошибка в логике или БД)».

    [HttpPost]
    public async Task<IActionResult> Create([FromBody] CreateStockDto dto) 
    {
        var model = dto.ToModel();
        await _context.Stocks.AddAsync(model);
        await _context.SaveChangesAsync();
        
        // Возвращаем 201 статус и путь к новому объекту
        return CreatedAtAction(nameof(GetById), new { id = model.Id }, model.ToStockDto());
    }
Суть: Ты возвращаешь не просто «объект или пустоту», а конкретный статус-код, чтобы фронтенд точно знал, выводить данные или показывать ошибку.
