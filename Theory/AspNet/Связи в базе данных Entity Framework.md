1. Primary Key (PK) — Первичный ключ
Это главный уникальный идентификатор строки в таблице. У него одна задача — гарантировать, что в этой таблице нет двух абсолютно одинаковых записей и каждую можно найти со 100% точностью.

На уровне БД: Чаще всего это просто число, которое автоматически увеличивается при создании новой строки (1, 2, 3...), либо уникальная строка (GUID). На одну таблицу может быть только один PK. По нему база данных ищет записи мгновенно.

На уровне C#: Это обычное свойство класса, которое чаще всего называется Id.
    
    C#
    public class Author
    {
        public int Id { get; set; } // Это наш Primary Key (PK)
        public string Name { get; set; }
    }

2. Foreign Key (FK) — Внешний ключ
Это специальное поле, которое связывает одну таблицу с другой. Это буквально «ссылка на паспорт» (PK) другой записи.

В реляционных базах данных связь всегда физически хранится на стороне «ребенка» (зависимой сущности). Книга не может существовать в воздухе — она обязана указать, какому автору принадлежит.

На уровне БД: В таблице Books создается колонка AuthorId. В неё можно записать только то число, которое уже существует в таблице Authors в колонке Id. Если ты попытаешься сохранить книгу с AuthorId = 99, а автора с таким ID в базе нет, БД выдаст ошибку и заблокирует запрос.

На уровне C#: Это обычное числовое свойство в зависимом классе.

    C#
    public class Book
    {
        public int Id { get; set; } // Собственный PK книги
        public string Title { get; set; }
        
        public int AuthorId { get; set; } // Это Foreign Key (FK). Ссылка на автора!
    }
3. Навигационные свойства (Navigation Properties)
А вот это — чистая магия Entity Framework Core. В самой базе данных никаких навигационных свойств не существует. Там есть только жесткие таблицы, ID и связи по циферкам.

Если бы мы работали с БД напрямую через SQL, то чтобы получить книгу вместе с автором, нам пришлось бы писать тяжелый запрос с оператором JOIN:

SQL
SELECT * FROM Books 
INNER JOIN Authors ON Books.AuthorId = Authors.Id;
Навигационные свойства созданы для того, чтобы C#-разработчик забыл про SQL и работал со связями как с обычными объектами в памяти.

Мы просто добавляем внутрь классов полноценные объекты друг друга:

    C#
    public class Author
    {
        public int Id { get; set; } // PK
        public string Name { get; set; }
    
        // НАВИГАЦИОННОЕ СВОЙСТВО (Коллекция): 
        // Позволяет у автора сразу посмотреть список его книг
        public List<Book> Books { get; set; } = new();
    }
    
    public class Book
    {
        public int Id { get; set; } // PK
        public string Title { get; set; }
        
        public int AuthorId { get; set; } // FK
    
        // НАВИГАЦИОННОЕ СВОЙСТВО (Одиночное): 
        // Позволяет у книги сразу прыгнуть в объект автора
        public Author Author { get; set; } 
    }
Как это меняет написание кода?
Благодаря навигационным свойствам, ты можешь писать элегантный код на LINQ.

Например, тебе нужно проверить, из какой страны автор конкретной книги. Без навигационного свойства тебе пришлось бы делать два запроса: сначала искать книгу, брать её AuthorId, потом по этому ID искать автора.

С навигационным свойством ты пишешь в одну строчку через точку:

    C#
    string country = currentBook.Author.Country; 
    // EF Core сам под капотом сделает нужный JOIN в базу данных!
    Или вытащить имена всех книг автора:
    
    C#
    var bookTitles = currentAuthor.Books.Select(b => b.Title);

2. Nullable связи и Каскадное удаление
Знак вопроса ? в типе данных меняет логику удаления:

int StockId (Required) → Акция удалена = Комментарии удалены автоматически (Каскад).

int? StockId (Optional) → Акция удалена = Комментарии остались, но связь стерта (NULL).

    public class Stock 
    {
        public int Id { get; set; } // Primary Key
        public string Symbol { get; set; } = string.Empty;
    
        // Навигационное свойство "к детям" (Коллекция)
        public List<Comment> Comments { get; set; } = new(); 
    }
    
    public class Comment 
    {
        public int Id { get; set; } // Primary Key
        public string Content { get; set; } = string.Empty;

    // --- ВАРИАНТ А: ОБЯЗАТЕЛЬНАЯ СВЯЗЬ (Required) ---
    // public int StockId { get; set; } 
    // Результат в БД: NOT NULL. 
    // Удаление акции => Удаление всех комментариев (Cascade Delete).

    // --- ВАРИАНТ Б: МЯГКАЯ СВЯЗЬ (Optional/Nullable) ---
    public int? StockId { get; set; } 
    // Результат в БД: NULL allowed.
    // Удаление акции => StockId у комментариев станет NULL (они выживут).

    // Навигационное свойство "к родителю" (Объект)
    // Позволяет писать: var name = comment.Stock.Symbol;
    public Stock? Stock { get; set; } 
    }

3. Жадная загрузка (Include) и Циклы в JSON
EF Core по умолчанию «ленивый» и не подгружает связанные данные. Метод .Include() заставляет его сделать JOIN в SQL.

Осторожно: Если модель ссылается на комментарий, а комментарий обратно на модель, возникнет Object Cycle, и JSON «сломается». Решение: Всегда используй DTO!

    C#
    // Правильное получение данных со связями
    var stocks = await _context.Stocks
        .Include(s => s.Comments) // Подгружаем "детей" одним JOIN-ом
        .Select(s => s.ToStockDto()) // Превращаем в DTO, разрывая циклы
        .ToListAsync();
